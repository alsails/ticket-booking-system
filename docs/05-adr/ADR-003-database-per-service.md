# ADR-003. Собственная база данных у каждого сервиса

Состояния заказа, фактических списаний и инвентаря билетов имеют разных владельцев и разные правила согласованности. Общая схема таблиц создала бы обход API организаторов и позволила бы одному компоненту несанкционированно изменять чужие брони или платежи. При этом **внутри** каждого отдельного сервиса необходимы локальные атомарные транзакции.

## Рассмотренные варианты

1. **Одна общая БД / общая схема.** Удобные `JOIN` и единые транзакции, но нарушает автономность и создаёт скрытую связанность изменений схемы.
2. **Один сервер PostgreSQL с раздельными схемами и правами.** Допустимый компромисс для разработки, но права и владение схемами нужно обеспечить строго; физический отказ сервера остаётся общим.
3. **Логически независимые БД на сервис с отдельными правами доступа.** Не позволяет обходить API и допускает самостоятельное развитие схемы; требует контракты и асинхронное согласование.

## Решение

Выбран **вариант 3**. У `Order Service` — `Order DB` (позиции заказа, статусы Saga, реестр `organizer_id`, шаги операций, inbox/outbox, идемпотентность). У `Payment Service` — `Payment DB` (списания, возвраты, связь с транзакциями провайдера, дедупликация webhook, outbox). Каждый `Organizer Booking Service` владеет **своей** `Organizer DB` (мероприятия, места, локальные брони, билеты, ключи идемпотентности).

Используем **PostgreSQL** и отдельные базы/учётные данные. Отдельные БД могут находиться в одном учебном Docker Compose, но ни один сервис не получает прав чтения и записи в таблицы другого. Обмен между владельцами данных идёт только через OpenAPI/AsyncAPI. У организатора локальная транзакция резервирования **всех мест одной команды** должна обеспечить отсутствие двойной продажи, в том числе при конкуренции с его собственным каналом.

## Последствия

**Преимущества:** единый владелец каждого инварианта, локальная ACID-гарантия резервирования, независимые миграции, более строгая изоляция коммерческих и платёжных данных.

**Издержки и риски:** нельзя объединить SQL-транзакции сервисов; невозможны межсервисные `JOIN` и внешние ключи. Order Service хранит только ссылки на внешние ресурсы и снимок цены, а не «свои» остатки. Для восстановления и мониторинга необходимы API сверки, корреляционные идентификаторы и Saga. Общий PostgreSQL-хост остаётся общей точкой отказа инфраструктуры, несмотря на логическую изоляцию.

## Проверка решения

- У пользователя БД Order Service нет доступа к таблицам организатора или Payment Service.
- Одновременные попытки занять один `seat_id` через API платформы и собственный канал дают один активный резерв/билет.
- Остановка одного экземпляра организатора не изменяет данные других экземпляров.
